## OBJECTIVE

Build a centralized management exception-monitoring dashboard that identifies operational and financial issues requiring attention.

This is the final planned functional addition before Phase 6E end-to-end verification.

Do not redesign the interface or change the existing color palette.

## 1. INSPECT EXISTING SERVICES

Review:
- OPERA monitoring and reconciliation
- Sage monitoring and reversal-required states
- Wallet refund requests and decisions
- Supervisor override requests
- Menu availability
- Staff order status and timestamps
- Management authorization
- Audit reporting

Reuse persisted records and existing services.

Do not fabricate exceptions or duplicate financial calculations.

## 2. CENTRAL EXCEPTION DASHBOARD

Create:

`/management/exceptions`

And a protected read-only API:

`GET /api/management/exceptions`

Display exceptions using actual persisted states, including:

- Exception category
- Severity
- Outlet
- Related reference
- Current status
- Time detected
- Explanation in plain English
- Recommended next step
- Link to the existing relevant management screen

Include summary counts, category filters, severity filters, outlet filters, date filters, and pagination.

Use deterministic severity rules. Document those rules rather than presenting arbitrary classifications as official business policy.

## 3. EXCEPTION SOURCES

Include, where supported by existing data:

1. Uncertain OPERA postings.
2. Rejected or unresolved OPERA postings.
3. Failed or uncertain Sage synchronization.
4. Sage refund reversals requiring reconciliation.
5. Pending supervisor overrides.
6. Pending wallet refund approvals.
7. Unavailable menu items as informational operational exceptions.

Do not classify every historical rejected attempt as an unresolved emergency. Distinguish genuinely actionable issues from closed or informational records.

Do not invent kitchen delays unless reliable timestamps and a documented threshold exist.

## 4. MANAGEMENT EXPERIENCE

Provide clear summary cards and a prioritized exception table.

Allow supervisors to navigate to the relevant existing workflow.

Do not create new transaction mutation mechanisms, unrestricted retry buttons, or automatic financial corrections.

Maintain responsive desktop and mobile behavior.

## 5. SECURITY AND AUDITING

Reuse the existing management authorization mechanism.

- Missing identity: 401
- Ordinary staff: 403
- Authorized supervisor: 200
- Invalid filters: 400

The API must be read-only.

Do not expose sensitive room, identity, verification, or financial secrets.
